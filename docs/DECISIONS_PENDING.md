- 2026-10-18 **Corporate actions: an ex-dated table instead of a periodic `adj_close` re-download** (task 190-corporate-actions). Chosen: store dividends and splits in `corporate_actions` by ex-date, captured from the daily download we already make (`actions=True`, no extra requests). Why: it is point-in-time (a row is known from its ex-date, so total-return labels in task 200 can't leak), it costs no extra yfinance calls, and the split rows let `detect_unadjusted_splits` / `python main.py dq` find history that was never re-adjusted (price rows are insert-only, so a split after the first ingest leaves older bars at the old scale). Notes: yfinance reports Indian **bonus issues as splits** (a 1:1 bonus is factor 2.0), and its **dividend amounts are adjusted for later splits**, so the stored value is per current share and is re-stated (updated in place) after a split. Ex-dates before the first stored bar are credited to the first bar by `dividends_on_bars`. Detection tolerance is `tol = 0.15` (relative) in `detect_unadjusted_splits`; a split with factor within ~15% of 1 can't be told apart from a gap. `dq` only reports; re-adjusting history is left to you (e.g. delete that asset's `price_daily` rows and re-ingest).
- 2026-10-18 **Incremental downloads: edges and trade-offs** (task 230-ingest-incremental-daily). Chosen: an asset with stored bars downloads `start = last stored bar date − overlap` (`DAILY_INCREMENTAL_OVERLAP_DAYS = 14`, `INTRADAY_INCREMENTAL_OVERLAP_DAYS = 5`). Judgment calls: (1) **60-day 15m edge**: Yahoo rejects a start of exactly 60 days back (midnight of that date is a few hours past 60 days), so the largest usable intraday start is 59 days back (`INTRADAY_MAX_LOOKBACK_DAYS = 60` in settings); a later start falls back to `INTRADAY_PERIOD`. (2) **Thin window**: if the download holds fewer sessions than `DAILY_REFRESH_SESSIONS` (or trading days than `INTRADAY_REFRESH_DAYS`), or is empty, it is replaced by one full-period download that is processed as before. (3) **New split**: when the incremental frame has a split with no stored (ex_date, "split") row, the asset is re-downloaded once with the full `DAILY_PERIOD` and the *actions* come from that frame (older dividends re-stated in place); prices still come from the incremental frame. If that re-download fails the split row is not stored, so the next run sees it as new and retries (storing it would freeze the old dividends). (4) **Trade-off you may want to change**: history older than the overlap is no longer re-fetched, so a rejected or missing old bar is not backfilled, and the `corporate_actions` rows of assets that already have price rows are only backfilled by a full download, which nothing triggers now (see the BACKLOG item for `ingest --full`). Alternative for (4): also go full when an asset has price rows but no `corporate_actions` rows (costs one 5y request per day for names that truly never had an action), or schedule a weekly full re-download. To switch, set the overlap constants huge (always effectively full) or add that rule in `_download_start`.
